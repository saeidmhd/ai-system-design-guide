# مدیریت تغییرات و ناپایداری فریم‌ورک‌ها (Framework Churn)

فریم‌ورک‌های ارکستراسیون هوش مصنوعی با سرعتی بسیار بالاتر از محتواهای آموزشی در حال تغییر و تحول هستند. پروژه‌های LlamaIndex و LangChain هر دو ساختار بسته‌های خود را در سال ۲۰۲۴ بازطراحی کردند و ساختارهای اصلی اولیه خود را ظرف یک سال به طور کامل حذف نمودند، و فریم‌ورک Haystack نیز در نسخه ۳.۰ خود در ژوئیه ۲۰۲۶ همین مسیر را طی کرد. نتیجه این است که دوره‌ای که تنها ۱۲ ماه پیش ضبط شده باشد، غالباً در همان نخستین خط `import` دچار شکست می‌شود. این صفحه به ریشه‌یابی این معضل، چرایی وقوع آن، و نحوه یادگیری و توسعه کد به‌گونه‌ای می‌پردازد که دانش و پروژه‌های شما در برابر این دگرگونی‌ها پایدار بمانند.

خلاصه یک‌خطی این مفهوم: **فریم‌ورک‌ها ابزار تحویل محصول در این فصل کاری هستند؛ اما ساختارهای بنیادین (Primitives) دارایی‌های ماندگار شما به شمار می‌روند. فریم‌ورک را قفل (Pin) کنید، و اصول بنیادین را بیاموزید.**

## جرقه اصلی: چرا یک آموزش در نصب تازه با شکست روبرو می‌شود <a id="the-trigger-why-a-course-breaks-on-a-fresh-install"></a>

یک مثال واقعی و متداول: کاربری یک دوره آموزشی معتبر و ویدیویی LlamaIndex را آغاز می‌کند، نخستین سلول نوت‌بوک را کپی می‌کند و با این پیام روبرو می‌شود:

<div dir="ltr">

```
ImportError: cannot import name 'SimpleDirectoryReader' from 'llama_index'
```

</div>

یا اندکی بعد:

<div dir="ltr">

```
TypeError: Can't instantiate abstract class OpenAI with abstract method _prepare_chat_with_tools
```

</div>

هیچ ایرادی در یادگیرنده یا ساختار آموزشی ضبط‌شده وجود ندارد. محیط اجرای نوت‌بوک دوره نسخه‌های قدیمی را قفل کرده است (یک دوره آموزشی محبوب LlamaIndex دارای فایل `requirements.txt` با نسخه‌های `llama-index==0.10.30` و `llama-index-llms-openai==0.1.26` است) و ویدیو با همان نسخه‌ها ضبط شده است. اما در اجرای دستور `pip install llama-index` روی سیستمی تازه، نسخه‌ای بسیار جدیدتر نصب می‌شود که مسیرهای ایمپورت و سلسله‌مراتب کلاس‌های آن تغییر یافته است. خطای اول ناشی از جابه‌جایی مسیر ایمپورت است؛ خطای دوم ناشی از عدم تطابق جزئی نسخه‌هاست که در آن بسته اصلی و بسته الحاقی همگام با یکدیگر به‌روزرسانی نشده‌اند و متد انتزاعی جدیدی به کلاس پایه افزوده شده که بسته الحاقی قدیمی هرگز آن را پیاده‌سازی نکرده است.

این مسئله نقص فریم‌ورک LlamaIndex یا ضعف دوره آموزشی نیست؛ بلکه پیامد طبیعی فریم‌ورک‌های با سرعت توسعه بالا در ترکیب با محتوای آموزشی ضبط‌شده و ثابت است. درک این مکانیزم به شما اجازه می‌دهد به جای ناامید شدن، ظرف چند ثانیه مشکل را برطرف کنید.

## چه تغییراتی رخ داده است <a id="what-actually-changed"></a>

### تصویر وضعیت در نوامبر ۲۰۲۶ <a id="the-november-2026-snapshot"></a>

ناپایداری و تغییر نسخه‌ها صرفاً آموزش‌ها را دچار اختلال نمی‌کند؛ بلکه کل قابلیت‌های محصولات را بازنشسته کرده و بدون تغییر کدهای شما، رفتار سیستم را دگرگون می‌سازد. دو فهرست زیر مربوط به رویدادهای اوت تا اکتبر ۲۰۲۶ باید در تقویم کاری ثبت شوند:

**سرویس‌های بازنشسته‌شده و مهلت‌های زمانی**

| تغییر رخ‌داده | تاریخ | معنا و پیامد آن |
|---|---|---|
| تعطیلی کامل **OpenAI Assistants API** | ۲۶ اوت ۲۰۲۶ (اجرا شده) | اندپوینت‌های `/v1/assistants`، بخش Threads و Runs اکنون خطا برمی‌گردانند (در OpenAI و Azure OpenAI). جایگزین رسمی Responses API و Conversations API است، در حالی که **هیچ مهاجرت خودکاری** برای Threads وجود ندارد. دیتابیس‌های برداری باقی ماندند، بنابراین تیم‌ها ارکستراسیون را بازنویسی کردند، نه ایندکس‌ها را. هر آموزشی که هنوز از Assistants و Threads استفاده می‌کند ساختاری مرده را آموزش می‌دهد |
| تعطیلی بخش‌های **OpenAI Evals، Agent Builder و Reusable Prompts** | هر سه در ۳۰ نوامبر ۲۰۲۶ خاموش می‌شوند (بخش ارزیابی‌ها از ۳۱ اکتبر حالت فقط‌خواندنی گرفت) | راهنمای رسمی اوپن‌ای‌آی کاربران را به Promptfoo هدایت می‌کند که اکنون به مالکیت OpenAI درآمده و با مجوز MIT عرضه می‌شود. کاربران Agent Builder به Agents SDK یا ChatGPT Workspace Agents هدایت می‌شوند |

| یک مدل یکسان، در کلودهای مختلف (**Same model, different clouds**) | روندی ادامه‌دار | مدل Claude Opus 4.1 در ۵ اوت ۲۰۲۶ از Claude API خارج شد اما در سرویس Bedrock تا ۸ ژانویه ۲۰۲۷ فعال است. برعکس، مدل Claude Sonnet 4.5 در ۳۰ نوامبر ۲۰۲۶ از Claude API خارج می‌شود در حالی که در Bedrock تا ۸ آوریل ۲۰۲۷ در دسترس خواهد بود. چرخه عمر را بر اساس جفت (مدل، پلتفرم) مدیریت کنید، نه صرفاً نام مدل |
| تغییرات مالکیت شرکت‌ها (**Ownership changes**) | شرکت Dynatrace تصاحب پلتفرم Arize را در ۱ اکتبر ۲۰۲۶ تکمیل کرد (با قیمت ۹۱۵ میلیون دلار)؛ ابزار Promptfoo اکنون بخشی از OpenAI است؛ شرکت NVIDIA خرید Hugging Face را تأیید کرد (با ارزش ۱۲.۹۳ میلیارد دلار) | ابزارهای مشاهده‌پذیری را انتخاب کنید که قابلیت استخراج داده‌های شما را داشته باشند، و دیتاست‌ها و مدل‌های وابسته را به‌صورت محلی ذخیره کنید |

|---|---|---|

| تغییر مجوز نرم‌افزاری SDK | نسخه‌های اصلی جدید SDK و CLI کلود (۲۱ اکتبر) | تمامی هشت نسخه اصلی جدید به مجوز Apache 2.0 تغییر یافتند (نسخه‌های قبلی با MIT بودند) |

| انتشار نسخه ۲.۰ پایتون MCP SDK | ۲۸ ژوئیه ۲۰۲۶ | دستور `pip install mcp` اکنون نسخه 2.x را نصب می‌کند و کلاس `FastMCP` به `MCPServer` تغییر نام یافته است؛ تا زمان تطبیق کدها نسخه را به `mcp<2` مقید کنید |

آموزه ماندگار: **هر چیزی را که به آن وابسته‌اید، از جمله شناسه‌های مدل‌ها را قفل (Pin) کنید، و در فید اعلان‌های بازنشستگی تک‌تک ارائه‌دهندگان عضو شوید.** بازنشستگی سرویس Assistants از یک سال قبل اعلام شده بود؛ بنابراین تیم‌هایی دچار بحران شدند که هرگز اطلاعیه‌ها را مطالعه نمی‌کردند. تغییرات بی‌صدا خطرناک‌تر هستند؛ زیرا تنها آزمون‌های ارزیابی و چک‌های تله‌متری قادر به شناسایی آن‌ها هستند.

سه بازطراحی اساسی جریان تغییرات اخیر را مشخص می‌سازند:

### فریم‌ورک LlamaIndex

- **نسخه v0.10 (فوریه ۲۰۲۴): تفکیک بزرگ.** بسته یکپارچه `llama-index` به `llama-index-core` (صرفاً انتزاع‌ها) به‌علاوه صدها بسته مجزای یکپارچه‌سازی تقسیم شد. مسیرهای ایمپورت دگرگون شدند:
  - انتقال از سطح بالا به هسته: `from llama_index.core import VectorStoreIndex`
  - انتقال افزونه‌ها به بسته‌های اختصاصی: `from llama_index.llms.openai import OpenAI`
- **نسخه v0.11 (اوت ۲۰۲۴): حذف ساختار نمادین.** کلاس `ServiceContext` در نسخه 0.10 منسوخ و در 0.11 *به‌طور کامل حذف* گردید. جایگزین رسمی آن شیء سراسری `Settings` است.

<div dir="ltr">

```python
  # OLD (pre-0.10, removed in 0.11)
  from llama_index import ServiceContext, set_global_service_context
  service_context = ServiceContext.from_defaults(llm=llm, embed_model=embed)
  set_global_service_context(service_context)

  # CURRENT
  from llama_index.core import Settings
  Settings.llm = llm
  Settings.embed_model = embed
  ```

</div>

- **جریان‌های کاری Workflows (نسخه ۱.۰ در ژوئن ۲۰۲۵، اکنون سری 2.x):** ارکستراسیون عاملی رویدادمحور و دارای وضعیت تایپ‌شده که در بسته `llama-index-workflows` عرضه شده است. در سپتامبر ۲۰۲۶ شرکت سازنده اعلام کرد تمرکز اصلی آن به سمت محصولات پارسینگ و استخراج اسناد معطوف شده است.
- **ابزار به‌روزرسانی خودکار:** دستور `llamaindex-cli upgrade <dir>` ایمپورت‌های قدیمی را به‌طور خودکار اصلاح می‌کند.

### فریم‌ورک LangChain

- **تفکیک بسته‌ها.** بسته `langchain-core` (رابط‌های پایه و Runnableها، تنها بسته با تضمین سازگاری به عقب)، بسته `langchain-community` (یکپارچه‌سازی‌های شخص ثالث)، بسته `langchain` (زنجیره‌ها و عامل‌ها)، و بسته‌های همکار به ازای هر تأمین‌کننده. زبان بیان LCEL (مدل پایپ با عملگر `|`) جایگزین زیرکلاس‌های قدیمی `Chain` شد.
- **نسخه v0.3 (سپتامبر ۲۰۲۴): مهاجرت از Pydantic نسخه ۱ به ۲.**
- **نسخه v1.0 (اکتبر ۲۰۲۵): پیاده‌سازی عامل‌ها بر بستر LangGraph.** روش استاندارد ساخت عامل به `create_agent` با اجرای روی رانتایم LangGraph تبدیل شد. زنجیره‌های قدیمی مانند `LLMChain`، `RetrievalQA` و `AgentExecutor` به بسته `langchain-classic` منتقل شدند.

### فریم‌ورک Haystack

- **نسخه 3.0 (ژوئیه ۲۰۲۶): محوریت عامل.** مؤلفه مجزای `ToolInvoker` حذف شد و `Agent` مدیریت ابزارها را با هوک‌های چرخه حیات، سیستم مهارت‌ها (Skills)، و هوک‌های تأیید انسانی در دست گرفت.
- **ادغام پایپ‌لاین‌ها و تفکیک اتصالات.** کلاس‌های پایپ‌لاین همگام و ناهمگام ادغام شدند و ۳۰ مؤلفه به بسته‌های مجزا انتقال یافتند.

## چرا آموزش‌ها و دوره‌ها منسوخ می‌شوند <a id="why-courses-and-tutorials-go-stale"></a>

دوره‌های ضبط‌شده و مقالات وبلاگی یک **تصویر لحظه‌ای** ثبت می‌کنند: ویدیو و فایل‌های `requirements.txt` در زمان ضبط ثابت می‌مانند؛ اما مخازن بسته این‌گونه نیستند. وقتی کاربر اقدام به نصب تازه می‌کند، پکیج منیجر نسخه‌های جاری را واکشی می‌کند که مدت‌ها از نسخه قفل‌شده دوره جلوتر رفته‌اند، و در نتیجه کد با API فعلی تطابق ندارد.

الگوهای شکست کاملاً قابل پیش‌بینی هستند:
- **ایمپورت‌های جابه‌جاشده**: سمبل به `.core` یا پکیج‌های همکار منتقل شده است.
- **سمبل‌های حذف‌شده**: ساختار به‌طور کامل دیلیت شده است (مانند `ServiceContext` یا `LLMChain`).
- **ناهماهنگی ناشی از ارتقای جزئی**: بسته هسته و افزونه از هم فاصله گرفته‌اند؛ راه‌حل ارتقای همزمان آن‌هاست (`pip install -U llama-index llama-index-llms-openai`).
- **مدل‌های منقضی‌شده**: دوره از شناسه‌های بازنشسته‌شده استفاده می‌کند (مانند `gpt-3.5-turbo-0301`).
- **پارامترهای حذف‌شده**: متدهایی که دیگر پارامترهایی مانند `temperature` را نمی‌پذیرند.
- **تغییرات رفتاری بی‌صدا**: تغییر مدل پیش‌فرض یا تله‌متری که هیچ استک‌تریسی ایجاد نمی‌کنند اما خروجی را دگرگون می‌سازند.

## آیا این آموزش به‌روز است؟ یک بررسی ۳۰ ثانیه‌ای <a id="is-this-tutorial-current-a-30-second-check"></a>

پیش از صرف ساعت‌ها زمان برای هر دوره آموزشی، مقاله یا نوت‌بوک:

۱. **تاریخ انتشار را با ریتم فریم‌ورک بسنجید.** یک آموزش LangChain یا LlamaIndex مربوط به اوایل سال ۲۰۲۴ ذاتاً قبل از بازطراحی‌های اساسی اخیر است.
۲. **فایل `requirements.txt` را باز کرده و نسخه‌ها را با نسخه فعلی مقایسه کنید.** نسخه `llama-index==0.10.x` در مقایسه با نسخه فعلی `0.14.x`، یا هر نسخه `langchain<1.0` یعنی منتظر خطا باشید.
۳. **کدها را برای سمبل‌های حذف‌شده جستجو (Grep) کنید:**
   - در LlamaIndex: واژه‌های `ServiceContext`، `LLMPredictor`، `set_global_service_context` یا ایمپورت از `llama_index` بدون پسوند `.core`.
   - در LangChain: واژه‌های `LLMChain`، `RetrievalQA`، `initialize_agent`، `AgentExecutor`.
   - در OpenAI: واژه‌های `client.beta.assistants`، `threads`، `runs`.
   - در پروتکل MCP: عبارت `from mcp.server.fastmcp import FastMCP` (که در نسخه ۲ به `MCPServer` تغییر نام یافت).
   - در DSPy: متدهای `dspy.Assert` و `dspy.Suggest` (در سری ۳ حذف شدند).
   - در کیت Anthropic SDK: ارسال `temperature=` یا `top_p=` به متد `messages.create`.
۴. **مستندات سریع (Quickstart) رسمی پروژه را منبع موثق قرار دهید**، و از آموزش‌های دیگر فقط برای فراگیری **مفاهیم** استفاده کنید نه کپی مستقیم کدها.

## بقا در میانه تغییرات: قفل نسخه، فایل Lock و ایزوله‌سازی <a id="surviving-churn-pin-lock-isolate"></a>

انضباط مهندسی که مانع از کار افتادن ناگهانی سیستم‌ها می‌شود:

- **نسخه‌های دقیق را قفل (Pin) کنید.** استفاده از وابستگی‌های شناور بدون نسخه بزرگ‌ترین عامل شکست است. حداقل وابستگی‌های مستقیم را با `==` ببندید.
- **از فایل Lock واقعی استفاده کنید** تا وابستگی‌های زنجیره‌ای نیز تثبیت شوند. ابزار [`uv`](https://docs.astral.sh/uv/) گزینه‌ای سریع و محبوب در سال ۲۰۲۶ است؛ ابزارهای Poetry و pip-tools نیز جاافتاده‌اند. فایل Lock را کامیت کنید.
- **بسته‌های تفکیک‌شده را به‌صورت یک مجموعه واحد قفل کنید.** در LangChain و LlamaIndex، هسته و تمام بسته‌های ارائه‌دهندگان باید همگام حرکت کنند.
- **هر پروژه را در محیط مجازی (Virtualenv) یا کانتینر مجزا ایزوله کنید.** هرگز بسته‌ها را در سطح سیستم‌عامل اصلی نصب نکنید.
- **هشدارهای Deprecation را جدی بگیرید.** هشدارها دقیقاً جایگزین جدید و نسخه حذف را اعلام می‌کنند. نادیده گرفتن هشدارها یعنی شکست ناگهانی در ارتقای بعدی.
- **شناسه‌های مدل‌ها را قفل کنید.** مدل‌ها را در تمام فراخوانی‌ها صریح مشخص کنید تا تغییر پیش‌فرض‌ها در ارتقای بسته‌ها هزینه شما را دگرگون نسازد.
- **تله‌متری را پس از هر ارتقا بررسی کنید.** اطمینان حاصل کنید تریس‌ها، شمارنده‌ها و داده‌ها هنوز ارسال می‌شوند.

## مقایسه: فریم‌ورک در برابر SDK خام در برابر لایه نازک سفارشی <a id="framework-vs-raw-sdk-vs-thin-layer"></a>

| سطح انتزاع | موارد کاربرد | هزینه‌ها و معایب |
|---|---|---|
| کیت SDK خام ارائه‌دهنده (**Raw provider SDK**) | زمانی که چند فراخوانی ساده به مدل دارید، پایدارترین ساختار و شفاف‌ترین استک‌تریس‌ها را می‌خواهید، یا کدهای کتابخانه‌ای می‌نویسید | باید بازیابی، حلقه عاملیت و آزمون‌های تلاش مجدد را خودتان کدنویسی کنید |
| فریم‌ورک‌های جامع (**Framework**) | زمانی که به تنوع بالای اتصالات (ده‌ها وکتور استور، لودرها) یا ساختارهای آماده RAG برای توسعه سریع نیاز دارید | افزایش شدید وابستگی‌ها، تریس‌های تودرتوی عمیق، ناپایداری در به‌روزرسانی‌ها |
| لایه اختصاصی نازک (**Thin layer**) | سیستم‌های محیط تولید که می‌خواهند بدون تغییر کدهای اصلی، مدل‌ها یا فریم‌ورک‌ها را تعویض کنند | نیاز به اندکی طراحی و زمان اولیه |

برای محیط پروداکشن، **لایه نازک سفارشی** نقطه تعادل است: به SDK ارائه‌دهنده (یا صرفاً `langchain-core`) وابسته شوید، آن را پشت اینترفیس اختصاصی خود بپوشانید، و جزئیات فریم‌ورک را در یک ماژول قابل تعویض متمرکز کنید.

## چه مفاهیمی در میان نسخه‌ها انتقال‌پذیر و ماندگارند <a id="what-transfers-across-versions"></a>

نیمه‌عمر API یک فریم‌ورک حدود یک سال است. اما نیمه‌عمر **مفاهیم زیربنایی** آن برابر با کل تاریخ این رشته است. بر اساس آن سرمایه‌گذاری کنید:

**مفاهیم ماندگار (عمیق بیاموزید):**
- **سازوکار RAG:** استراتژی تکه‌تکه کردن متن (Chunking)، بردارسازی و جستجوی شباهت، بازیابی، بازرتبه‌بندی (Re-ranking)، و مثلث ارزیابی ارتباط با زمینه، وفاداری، و مرتبط بودن پاسخ. این اصول با هر تغییر نام در کلاس‌های فریم‌ورک زنده می‌مانند.
- **حلقه عاملیت:** فراخوانی مدل، انتخاب ابزار، اجرای ابزار، دریافت خروجی، تکرار، به‌علاوه مدیریت وضعیت، حافظه و مداخله انسانی. چه نام آن `AgentExecutor` باشد، چه `create_agent` و چه یک حلقه `while` دست‌نویس، ماهیت یکسان است.
- **ساختارهای بومی ارائه‌دهندگان:** ابزارها و Function Calling، خروجی‌های ساختاریافته، استریمینگ، و مدیریت سقف توکن‌ها و زمینه.
- **انضباط مهندسی نرم‌افزار:** فایل‌های قفل، محیط‌های تکرارپذیر، مطالعه گزارش‌های تغییرات، و پایپ‌لاین‌های ارزیابی.

**مفاهیمی که ماندگار نیستند (بیش از حد وقت تلف نکنید):** مسیر دقیق ایمپورت‌ها، نام کلاس‌ها، امضای متد سازنده‌ها، و شیء تنظیمات سراسری این ماه (`ServiceContext` در برابر `Settings`). به خاطر سپردن این‌ها انباشت یک دارایی مستهلک‌شونده است.

## استراتژی مهاجرت در هنگام الزام به ارتقا <a id="migrating-when-you-must-upgrade"></a>

هنگامی که مجبور به ارتقای یک پایگاه کد عملیاتی هستید:

۱. **ارتقا را در یک شاخه مجزا و از فایل Lock آغاز کنید**، پله به پله در نسخه‌های اصلی (مثلاً از 0.10 به 0.11 و سپس 0.12).
۲. **از ابزارهای رسمی بازنویسی کد (Codemod) استفاده کنید** (مانند `llamaindex-cli upgrade`)، و سپس بر اساس خطاهای ایمپورت پیش بروید.
۳. **از بسته‌های پل رابط (Bridge Packages)** (مانند `langchain-classic` یا `llama-index-legacy`) استفاده کنید تا برنامه حین مهاجرت گام‌به‌گام به کار خود ادامه دهد.
۴. **رفتار سیستم را با یک سوییت ارزیابی (Eval Harness) اعتبارسنجی کنید**، نه صرفاً با موفقیت ایمپورت‌ها. ارتقایی که کامپایل شود اما کیفیت بازیابی یا نرخ موفقیت عامل را کاهش دهد، یک پسرفت خاموش است. بخش [ارزیابی LLMها](../14-evaluation-and-observability/01-llm-evaluation.md) را ببینید.

## راهنمای جامع یادگیری پایدار <a id="a-durable-learning-playbook"></a>

۱. **حلقه عاملی را یک بار از طریق SDK خام بسازید**، بدون فریم‌ورک، تا متوجه شوید فریم‌ورک‌ها چه کارهایی را خودکار می‌کنند. پس از آن خطاهای فریم‌ورک را بسیار سریع‌تر عیب‌یابی خواهید کرد.
۲. **سپس برای سرعت از یک فریم‌ورک استفاده کنید**، اما با API آن به‌عنوان یک قطعه قابل تعویض پشت یک اینترفیس نازک رفتار کنید.
۳. **تمام وابستگی‌ها را قفل کنید، فایل Lock را کامیت نمایید و هشدارهای سیستم را روشن بگذارید.**
۴. **به جای حفظ مجدد، اصول را بازتولید کنید.** هنگامی که فریم‌ورک نام‌ها را عوض می‌کند، API جدید را به اصل سازنده آن نگاشت کنید («متد `create_agent` همان حلقه عاملیت روی LangGraph است»).
۵. **تازگی دوره‌ها را پیش از ثبت‌نام ارزیابی کنید.** از دوره‌های قدیمی فقط برای درک مفاهیم و از مستندات رسمی برای نوشتن کد استفاده نمایید.

برای مشاهده دوره‌های ممیزی‌شده، به [فایل معرفی دوره‌ها](../COURSES.md) مراجعه کنید. دلیل اعتبارسنجی تاریخی آن فایل دقیقاً تغییرات دائمی شرح‌داده‌شده در این فصل است.

## پرسش‌های مصاحبه <a id="interview-questions"></a>

### پرسش: یکی از همکاران از یک آموزش شش‌ماهه LlamaIndex استفاده کرده و کد در مرحله import با خطا مواجه می‌شود. توضیح دهید چه اتفاقی افتاده و چگونه آن را اصلاح می‌کنید؟

**پاسخ قوی:**
آموزش با یک نسخه قفل‌شده قبلی ضبط شده است و نصب تازه نسخه‌ای جدیدتر را نصب کرده که ساختار دایرکتوری آن دگرگون شده است. از نسخه 0.10 فریم‌ورک LlamaIndex به هسته `llama-index-core` و بسته‌های مجزای اتصالات تفکیک شده است؛ بنابراین ایمپورت از سطح ریشه مانند `from llama_index import SimpleDirectoryReader` باید به `from llama_index.core import SimpleDirectoryReader` تبدیل شود، و کلاس `ServiceContext` در نسخه 0.11 حذف شده و شیء سراسری `Settings` جایگزین آن گردیده است. اگر خطا مربوط به کلاس انتزاعی OpenAI باشد، ناشی از ارتقای نامتقارن بسته هسته و افزونه است که با ارتقای همزمان هر دو حل می‌شود. راه‌حل پایدار، استفاده از فایل Lock قفل‌شده برای بازتولید دقیق محیط، و مطالعه راهنمای مهاجرت نسخه است. در درازمدت به همکارم پیشنهاد می‌کنم از راهنمای رسمی سایت برای کدنویسی و از آموزش‌ها صرفاً برای یادگیری مفاهیم استفاده کند.

### پرسش: با توجه به سرعت بالای تغییرات در این فریم‌ورک‌ها، چگونه تصمیم می‌گیرید که اصلاً از یک فریم‌ورک استفاده کنید یا خیر؟

**پاسخ قوی:**
من ارزش واقعی ارائه‌شده توسط فریم‌ورک را ارزیابی می‌کنم. هدف اولیه این فریم‌ورک‌ها یکپارچه‌سازی تفاوت‌های API مدل‌ها بود، اما امروزه استانداردهای Function Calling و خروجی‌های ساختاریافته در SDKهای رسمی تثبیت شده‌اند و آن ارزش اولیه کمرنگ شده است. اگر به تنوع بالایی از اتصالات به پایگاه‌های برداری و بارگذارها یا ابزارهای آماده نیاز باشد تا سریع‌تر به نتیجه برسیم، فریم‌ورک ارزش هزینه خود را دارد. اما اگر صرفاً چند فراخوانی مشخص به مدل داریم یا کدهای کتابخانه‌ای می‌نویسیم، کیت خام SDK بسیار پایدارتر و خطایابی آن آسان‌تر است. در محیط پروداکشن معمولاً SDK را پشت یک لایه نازک سفارشی قرار می‌دهم تا تعویض مدل یا فریم‌ورک تنها یک ماژول را متأثر کند. در هر صورت، همه چیز را قفل می‌کنم؛ زیرا فرض من این است که APIهای مصوب این فصل کاری در فصل بعد منسوخ خواهند شد.

### پرسش: هزینه هر وظیفه یک Agent به‌طور ناگهانی ۴۰ درصد افزایش یافته و لحن پاسخ‌های آن در طول شب تغییر کرده است، در حالی که هیچ تغییر کد یا وابستگی از سمت شما رخ نداده است. چه اتفاقی افتاده و چگونه مانع تکرار آن می‌شوید؟

**پاسخ قوی:**
«بدون تغییر از سمت ما» معمولاً به این معناست که تغییری رخ داده که ما آن را *قفل نکرده بودیم*. نخستین بررسی‌های من: آیا مدلی به‌صورت ضمنی تغییر یافته است (یک مقدار پیش‌فرض در SDK یا مهارکننده، استفاده از آلیاس‌های شناور مانند `-latest`، یا ارتقای خودکار کلودها مانند تغییر خودکار نسخه‌های `gpt-4o` به `gpt-5.6-sol` در مایکروسافت فاندری)، آیا نسخه‌ای از ابزارهای CLI در CI یا ماشین توسعه‌دهندگان آپدیت شده است (مانند تغییر مدل پیش‌فرض در Claude Code و Codex CLI در سپتامبر ۲۰۲۶)، و آیا ارائه‌دهنده در سمت سرور خود تغییری اعمال کرده است؟ اگر سیستم ردگیری (Tracing) مدل پاسخ‌دهنده را ثبت کند فوراً مسئله روشن می‌شود، به همین دلیل من همواره شناسه مدل گزارش‌شده از سمت ارائه‌دهنده را لاگ می‌کنم نه نام درخواستی خودم را. راهکار پیشگیری سه گام است: تعریف صریح شناسه‌های مدل‌ها در تمام کدها، قفل کردن دقیق نسخه‌های SDK و ابزارهای عاملی همراه با درگاه ارزیابی پیش از ارتقا، و تعریف سیستم‌های هشدار روی هزینه، تعداد توکن‌ها و نرخ اصابت کش تا تغییرات ناخواسته در همان روز شناسایی شوند.

### پرسش: معماری یک رجیستری مدل (Model Registry) را طراحی کنید که در برابر تقویم‌های بازنشستگی متناقض میان ارائه‌دهندگان و کلودها پایدار بماند.

**پاسخ قوی:**
نکته کلیدی در تعریف واحد داده است: رکورد چرخه حیات باید به ازای جفت (مدل، پلتفرم، منطقه) ثبت شود نه صرفاً برای هر مدل؛ زیرا یک مدل مشابه اکنون در تاریخ‌های متفاوتی در API شرکت سازنده، AWS Bedrock، Google Cloud و Azure Foundry بازنشسته می‌شود (برای مثال Claude Opus 4.1 در اوت ۲۰۲۶ از API کلود خارج شد اما در Bedrock تا ژانویه ۲۰۲۷ فعال است). هر رکورد شامل شناسه قفل‌شده، حداقل تاریخ انقضا، تاریخ اعلام‌شده بازنشستگی، سیاست اعلام تغییرات تأمین‌کننده، و مدل جایگزین تأییدشده در سوییت ارزیابی است. یک جاب روزانه صفحات تغییرات و مستندات را اسکن کرده و مغایرت‌ها را مشخص می‌کند. هشدارهای سیستم در بازه‌های ۹۰، ۶۰ و ۳۰ روز قبل از انقضا فعال می‌شوند، و یک مسیر پشتیبان (Failover) تنها در صورتی معتبر است که مدل مقصد آن زودتر از مدل اصلی بازنشسته نشود. همچنین در مورد قوانین حالت Legacy در Bedrock که دسترسی پس از ۱۵ روز بی‌تحرکی قطع می‌شود، ترافیک مصنوعی دوره‌ای (Heartbeat) تعریف می‌کنم.
